# Local Comparator isolation compatibility

This directory records a local compatibility adapter for the verification
host. It does not modify Lean, Lake Comparator, bubblewrap, the proof sources,
or Palomar's official runner. These notes describe isolation checks; they do
not by themselves report a Comparator verdict or registry acceptance.

- File: `bwrap-private-network.py`.
- SHA-256:
  `be116b0142850cf2d8a6cd4f3f6c881ab0762b39aee2656d13b9f991bf3b54e4`.
- Actual shebang: `#!/usr/bin/python3`.
- Host tools observed: bubblewrap 0.12.0 and util-linux unshare 2.41.5.
- Lean source inspected: the installed `v4.35.0-rc2`
  `lake/Lake/CLI/Check.lean`, especially `buildSandboxArgs` and
  `sandboxSpawnArgs`.

The adapter was frozen before the current Comparator run. An isolated Python
startup (`-I`) was suggested as additional protection against Python startup
customization, but is **not** part of this frozen version. The coordinator
reported that the invoking environment and Python startup locations are
controlled and no custom Python import path is configured. Lake invokes its
selected sandbox executable through `env -i`. This report does not silently
attribute `-I` to the actual adapter.

## Reason for the adapter

On this host, the original no-network invocation reaches bubblewrap's
loopback initialization and fails with:

```text
bwrap: loopback: Failed to create NETLINK_ROUTE socket: Operation not permitted
```

Creating a new network namespace with `unshare` succeeds. The adapter creates
that fresh namespace before starting bubblewrap, then asks bubblewrap to
retain it. The retained namespace belongs to that invocation; it is not the
invoking host's network namespace. No interface, veth pair, bridge, address,
or route is added. Every adapted invocation is offline, including the
dependency-resolution stage to which unmodified Comparator grants network
access. Missing dependencies therefore cause failure rather than a fallback
to host networking.

The effective process chain is:

```text
official Comparator -> env -i -> adapter -> exec unshare
  --user --map-current-user --net -- /usr/bin/bwrap ...
```

The adapter parses only the option forms generated by this pinned Lake,
using their arities. In particular, an option value equal to `--` is not
mistaken for the command boundary. Immediately before the real boundary it
adds `--share-net --cap-drop ALL`; every original option and every payload
argument remains intact. Ordering matters: bubblewrap's `--unshare-all`
enables network unsharing, so the added `--share-net` must follow it.

It requires the original `--unshare-all`, `--die-with-parent`,
`--new-session`, and `--clearenv` options. It accepts no descriptor-taking
options and closes all inherited descriptors numbered 3 or above. It uses
absolute executable paths and `exec`, with no extra shell, background
launcher, or `unshare --fork` process. The existing read-only root, private
mount/PID/IPC/UTS namespaces, home-directory masks, explicit writable binds,
environment clearing, and lifecycle/session options are retained. Neither
`--no-sandbox` nor `--not-a-security-boundary` is used.

## Important findings from the independent investigation

An initially considered `--map-root-user` variant required explicit
capability removal. The observed payload had
`CapPrm = CapEff = CapBnd = 000001ffffffffff` without `--cap-drop ALL`.
Adding that option made all five reported capability sets zero. The actual
adapter uses `--map-current-user`, preserving UID 1000 in the tested
environment, and also explicitly drops all capabilities.

This difference is explained by bubblewrap 0.12.0's `acquire_privs` and
`drop_all_caps`: a real UID of zero defaults to retaining effective
capabilities unless explicitly changed. Its payload also intentionally
inherits otherwise-open descriptors; the descriptor cleanup performed for
the PID-1 reaper is not a cleanup of the final payload's inherited
descriptors. Closing extra descriptors in the adapter therefore prevents
pre-existing socket, directory, or namespace descriptors from crossing this
boundary. The relevant primary source is
[bubblewrap v0.12.0](https://github.com/containers/bubblewrap/blob/v0.12.0/bubblewrap.c).

## Observed small probes

`probe-results.json` is an explicitly labeled **summary of observed results**,
not a reconstructed raw transcript. The independent probes ran short Python
payloads only. They did not run Lean, compile proof files, or change official
tools. Temporary canaries were removed after the checks.

| Probe | Observed result |
| --- | --- |
| Original `bwrap --unshare-all`, no shared network | Failed at the denied `NETLINK_ROUTE` socket, before the payload. |
| Fresh outer network namespace, `--map-current-user`, original bubblewrap restrictions and `--share-net` | Succeeded as UID/GID 1000; all capability sets zero. |
| Fresh outer namespace, `--map-root-user`, with `--cap-drop ALL` | Succeeded as UID/GID 0; all capability sets zero. |
| Namespace and process observations | Independent user/net/mount/PID/IPC/UTS/cgroup namespace identifiers in the namespace probe; payload PID 2 with parent PID 1; only PIDs 1 and 2 visible in the filesystem probe. |
| Network observations | `/proc/net/dev` listed only `lo`; `/proc/net/route` was empty. |
| Read-only root | Writing a self-created canary outside the writable grant returned `EROFS` (30); host content remained unchanged. |
| Hidden home | A self-created file under `/home/agent` was invisible; its host content remained unchanged. |
| Intended writable areas | `/tmp/home` and an explicitly bound temporary `granted` directory were writable. |
| Existing host protections | `NoNewPrivs=1` and `Seccomp=2` remained present. |
| Deliberately inherited host network-namespace FD | The model adapter closed it; the payload saw only descriptors 0, 1, and 2. No namespace-joining operation was attempted. |
| Argument-boundary test | A `--setenv` value equal to `--`, and payload arguments `--share-net`, `--`, and `payload`, arrived unchanged. |

The independent parser/descriptor model used the root-mapped variant with
capabilities explicitly dropped. The separate nonroot control verified
`--map-current-user`. These were not represented as executions of the later
frozen adapter file.

The coordinator subsequently ran the actual adapter. Its separately retained
`wrapper-probe.log` reports UID 1000, all five capability sets zero, only
loopback, an empty route table, and `connect_ex("192.0.2.1", 443) = 101`
(`ENETUNREACH`). The independent reviewer read that log; the outbound-connect
probe was not part of the independent probes above.

## Scope of the conclusion

The observed adapter preserves Lake Comparator's namespace/mount/process
restrictions and makes Comparator's normally network-enabled dependency
phase offline as well. It does not introduce a path back to the host network
or a new writable host mount. No ambient host capability or extra inherited
descriptor was present in the tested payloads.

These are functional checks of the specified configuration, not a proof of
the absence of Linux or bubblewrap implementation vulnerabilities. Network
namespaces do not independently prohibit pathname-based Unix-domain sockets
reachable through the mounted filesystem; the adapter retains Comparator's
existing filesystem masks rather than claiming a new general socket-filter
policy. The lifecycle options were checked for preservation in the argument
list, not by a separate parent-killing experiment. Success of official
Palomar verification must be reported separately from this local host
compatibility work.
